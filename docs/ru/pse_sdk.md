## Концепция и архитектура SDK

**Portal Solver Editor SDK** реализует **Stateless** _(не хранящую состояние)_ модель **межпроцессного взаимодействия** _(IPC)_

### Что это значит на практике?

**SDK** является чистым транспортным и интерфейсным слоем. Он не владеет информацией о текущем игровом контексте: ему "неизвестно", какие объекты сейчас активны, какие триггеры сработали или в каком состоянии находятся элементы игры

SDK не кэширует данные, не хранит внутренние переменные состояния и не ведет учет игровых сущностей

Управление состоянием, выполнение, и вся прикладная логика выполняются исключительно на стороне хоста - игры **Portal: Solver**

### Ключевая задача SDK

Абстрагировать архитектурную сложность прямой работы с разделяемой памятью _(Shared Memory)_ и кольцевыми буферами _(Ring Buffers)_

Также SDK предоставляет разработчику готовые типизированные инструменты: структуры _(struct)_, перечисления _(enum)_ и вспомогательные функции _(хелперы)_ для безопасного и удобного чтения и записи

- **SDK как инструмент:** Предоставляет API для низкоуровневого обмена данными. Он берет на себя атомарную синхронизацию и разметку памяти
- **Разработчик как архитектор:** Проектирует логику интеграции.  Вы самостоятельно определяете, когда, в какой последовательности и на основе каких игровых событий отправлять команды или считывать буферы

## Но не пугайтесь этого!

Да, на первый взгляд идея "у нас нет кнопок, у нас есть только сырые байты" звучит дико и даже пугающе. Кажется, что придется вручную высчитывать каждый бит

Но на самом деле все гораздо проще, логичнее и... красивее. SDK берет на себя всю грязную работу по синхронизации потоков, барьерам памяти и работе с операционной системой. А для удобства сборки пакетов у вас будут перечисления и структуры-трафареты

Также в документации будут расписаны все смещения и индексы

Давайте посмотрим, как выглядит классический цикл **"Hello, World!"** на живом примере

## Быстрый старт

Взаимодействие с игрой всегда строится по одному сценарию: мы берем универсальную **64-байтовую структуру PseData**, задаем в нее команду _(заголовок)_, заполняем оставшиеся 60 байт полезными данными и отправляем в SDK _(в кольцевой буфер)_

Вот как выглядит минимальный рабочий код на **C++**, который подключается к игре, создает кнопку, затем отключается:
```cpp
#include <stdio.h>
#include <stdint.h>

#include "pse.h"
#include "pse.hpp"

int main() {
  printf("[SDK] Запуск и инициализация...\n");
  
  // 1. Подключаемся к Shared Memory, которую для нас уже создала игра
  // Если игра не запущена, функция вернет ошибку
  if (pseInitializeBuffers() != 0) { 
      printf(stderr, "[SDK] Ошибка: Игра не запущена или Shared Memory недоступна!\n");
      return -1;
  }
  printf("[SDK] Успешно инициализировали память игры!\n");
  
  // 1: Инициализация игры
  {
      // Создаем пустую 64-байтовую структуру на стеке
      PseData data{};
      
      // Заполняем заголовок пакета. Говорим игре: "Команда: Проинициализироваться!"
      data.header = PSE_COMMAND_GAME_INITIALIZE;
      
      printf("[SDK] Отправляем запрос на инициализацию...\n");
      
      // Отправляем команду и блокируем поток, пока игра не выполнит ее
      // Игра сотрет нашу команду и запишет результат прямо в это же поле header!
      pseCommandBufferSinglePushAndWait(&data);
      
      if (data.header != PSE_RESULT_SUCCESS) 
      {
          printf("[SDK] Ошибка инициализации игры! Код ошибки: 0x%08X\n", data.header);
          pseDeinitializeBuffers();
          return -1;
      }
      printf("[SDK] Игра успешно инициализирована!\n");
  }
  
  // 2: Создание динамического меша (плоскости)
  {
      PseData data{};
      
      // [Команда] Создать динамический меш
      data.header = PSE_COMMAND_DYNAMIC_MESH_CREATE;
      
      // Шаблон pse::Data::set<Смещение, Тип> красиво
      // и безопасно упаковывает данные в сырые 60 байт полезной нагрузки
      // Никакого ручного сдвига байт - хелпер сам знает размеры типов
      
      // [Смещение  0] Позиция, поворот и масштаб объекта на сцене
      // Занимает первые 40 байт полезной нагрузки
      pse::Data::set<0, PseTransform>(
          data, 
          PseTransform{
              PseQuat{}, 
              PseVector3{-400.0f, -400.0f, -100.0f}, // Координаты X, Y, Z
              PseVector3{1.0f, 1.0f, 1.0f}           // Масштаб меша
          }
      );
      
      // [Смещение 40] Задаем геометрию меша
      pse::Data::set<40, PseMesh>(data, PSE_MESH_FACE);
      
      // [Смещение 42] Задаем материал (текстуру пола)
      pse::Data::set<42, PseMaterial>(data, PSE_MATERIAL_FLOOR_WHITE);
      
      // [Смещение 44] Флаг видимости (Visibility). 1 - объект сразу отображается в игре
      pse::Data::set<44, int8_t>(data, 1);
      
      printf("[SDK] Отправляем команду на создание меша...\n");
      
      // Снова толкаем пакет в буфер и ждем ответа от игры
      pseCommandBufferSinglePushAndWait(&data);
      
      if (data.header != PSE_RESULT_SUCCESS)
      {
          printf("[SDK] Не удалось создать меш! Код ошибки: 0x%08X\n", data.header);
          pseDeinitializeBuffers();
          return -1;
      }
      printf("[SDK] Динамический меш успешно создан и отображен на сцене!\n");
  }
  
  // 3. Чистим за собой и корректно закрываем дескрипторы памяти перед выходом
  pseDeinitializeBuffers();
  printf("[SDK] Работа завершена. Отключено\n");
  return 0;
}
```

###### P.S. Можно использовать и чистый C, просто тогда нужно будет заменить шаблонные хелпер-функции `pse::Data::set` на `memcpy` аналоги и самому считать размер и смещения байт

## Что дальше?

Вы успешно освоили базовый принцип работы **Portal Solver Editor SDK**! 

Теперь перед вами открыты все дороги, и выбор направления зависит от ваших текущих целей и желаний:

- **Хотите изучить теорию и разметку?** Переходите к изучению Концепций и элементов в разделе **[Concept](concept/index.md)**. Там подробно расписано, какие битовые маски и смещения нужны для управления конкретными элементами в игре - от простых дверей до панелей веры
- **Нужен строгий справочник по коду?** Загляните в раздел **[Reference](reference/index.md)**. Это полный технический паспорт проекта, где собраны все структуры, перечисления, сигнатуры функций
- **Хотите сразу посмотреть живой рабочий код?** Отправляйтесь в папку `examples/` в корне репозитория. Там лежат готовые, компилируемые примеры под разные сценарии использования - от простых одиночных команд до сложного **Raw-управления** кольцевым буфером
- **Пишете не на C/C++?** Вернитесь в главный **[README.md](../../README_RU.md)** проекта. Там вы найдете постоянно обновляемый список биндингов и оберток от сообщества под другие языки программирования _(Rust, C#, Go и др.)_. Возможно, кто-то уже написал удобный инструмент для вашего любимого языка!
